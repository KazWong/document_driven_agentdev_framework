# AI Agent Development Framework v2.1.0 Architecture Specification

Status: **pre-implementation consolidated design baseline**
Last updated: **2026-10-01**

## 1. Purpose

v2.1.0 is an architectural consolidation of the AI Agent Development Framework. Its purpose is to remove technology-specific assumptions from framework core, make project requirements and engineering decisions traceable, make test/runtime environments modular and maintainable, and make the framework capable of developing and verifying itself using the same process that it imposes on managed projects.

This specification consolidates the design discussions and supporting design documents in this directory. It distinguishes **CONFIRMED** architecture from **PROVISIONAL/OPEN** proposals that still require explicit user confirmation before implementation hardcodes them.

The implemented current-release architecture remains described by `docs/architecture.md` until v2.1.0 is actually implemented and accepted.

## 2. Release baseline and compatibility intent

The intended release path is a consolidated architectural v2.1.0 rather than another sequence of v2.0.x domain-specific hotfixes.

The compatibility boundary is the **project**, not transparent preservation of every historical work-item implementation detail. A project created by an older framework release must remain maintainable. Historical work-item state may be converted by an explicit deterministic migration/conversion tool when required.

The design must not preserve obsolete project-type classification merely to maintain compatibility.

## 3. Non-negotiable architecture principles

### 3.1 Technology-neutral core

Core must not contain special branches for ROS, firmware, Python projects, C++, CUDA, game engines, browser stacks, or other domain/toolchain names. Technology-specific semantics belong in provider contracts and managed environment projects.

A recurring architecture test is:

> If adding support for a new software technology requires adding its technology name or special-case lifecycle control flow to framework core, the abstraction is incomplete.

### 3.2 Neutral project creation

`project create` creates a neutral framework/repository envelope. It does not choose C/C++/Python/ROS/etc. scaffolding as a core project type. Planner derives repository architecture from the approved requirements and provider capabilities.

### 3.3 Project is not a language or domain

A project is a repository/product with requirements, architecture, implementation, tests, evidence, and lifecycle. Languages, SDKs, runtimes, toolchains, and simulators are project/provider/environment concerns.

### 3.4 Universal traceability

Requirements traceability is a core framework specification for every managed project regardless of size. Minimum stable identity classes are:

- `REQ-*` — requirements;
- `CMP-*` — components;
- `IFACE-*` — interfaces;
- `VER-*` — verification obligations.

Additional implementation/test/work identities such as `TASK-*`, `TEST-*`, and `IMP-*` may be used.

The intended end-to-end chain is:

```text
REQ
  -> CMP / IFACE
  -> Plan
  -> IMP / implementation trace
  -> Candidate SHA
  -> VER
  -> TEST / verification execution
  -> Evidence
```

Every applicable requirement must end in an explicit disposition. Requirements must not silently disappear during replanning or implementation.

### 3.5 Framework self-development

The framework repository itself is a framework-managed project. Future framework architecture changes must follow ProjectBlueprint, feasibility, human approval, implementation, candidate, verification, review, promotion, and traceability rules. A stable/recovery boundary must prevent a candidate framework from approving or redefining the lifecycle that governs its own promotion.

## 4. ProjectBlueprint

### 4.1 Blueprint versus Plan

The **ProjectBlueprint** is the approved resulting architecture: what the project should be after the change.

The **Plan** is the work required to move the current project state to that Blueprint.

They are separate because implementation procedure can change without necessarily changing architecture, while an architecture change must be visible and approval-bound.

### 4.2 Planner ownership

Planner creates and revises ProjectBlueprint. Blueprint contains, as applicable:

- project requirements and constraints;
- components and responsibilities;
- interfaces and integration boundaries;
- repository-level structural architecture;
- provider/capability requirements;
- environment/deployment/runtime requirements;
- verification obligations;
- risk/consequence facts;
- traceability relationships;
- assumptions and declared scope.

Planner may propose complete declarative design artifacts for approval, including schemas, interface definitions, Mermaid/UML views, configuration contracts, API/data/message definitions, and environment requirements.

Planner must not implement production logic, Tester-owned tests, provider environment implementation, or silently mutate the product repository before approval.

### 4.3 Interfaces are first-class

Interfaces are not merely prose. Blueprint may identify APIs, CLI contracts, data/file formats, message definitions, configuration schemas, network protocols, plugin/provider interfaces, hardware boundaries, or other integration contracts using stable `IFACE-*` identities.

### 4.4 Verification obligations

Blueprint defines **what must be proven** with stable `VER-*` obligations. Tester defines **how it is proven** with concrete test designs/cases/evidence strategy.

### 4.5 Environment authority

Material deployment/test/runtime target choices are user-authoritative. If ambiguous, Planner asks unless the user explicitly delegates the choice. A delegated choice must be concrete, documented with rationale, and included in the approval package. A provider cannot silently substitute an incompatible target.

Changing a user-approved compatibility target is an architecture change. Rebuilding a compatible environment generation for the same target is environment lifecycle work, not automatically an application architecture change.

## 5. Engineering Change Package and approval

Human approval applies to a versioned **Engineering Change Package (ECP)** rather than a standalone prose plan.

An approval-ready ECP binds at least:

- authoritative request/document revision;
- applicable requirements;
- ProjectBlueprint revision;
- Plan revision;
- provider/environment requirements;
- Provider feasibility facts;
- Tester testability/test-design result;
- Coder implementation-feasibility result;
- implementation scope;
- verification obligations;
- risk/permission assessment;
- traceability coverage;
- assumptions/deviations.

### 5.1 Pre-approval flow

```text
User requirements / project knowledge
              |
              v
            Planner
              |
              v
      Draft Blueprint + Plan
              |
      +-------+--------+
      |                |
      v                v
Provider feasibility  Tester testability/design
      |                |
      +-------+--------+
              |
              v
       Coder feasibility
              |
              v
     Planner reconciliation
              |
              v
   Approval-ready ECP
              |
              v
       Human approval
```

Draft revisions may iterate before approval without requiring repeated human approvals.

### 5.2 User edits

Users may edit semantic project knowledge and proposal content. A semantic edit creates a new unapproved package revision and reruns affected validation/feasibility before final approval.

Framework-managed identity/integrity fields such as stable IDs, hashes, candidate bindings, provenance, approval identity, and evidence bindings are not ordinary user-editable semantic content.

### 5.3 Post-approval replan

A real Planner revision of approval-bound Blueprint/Plan content after approval creates a new ECP revision and requires human reapproval. Internal Coder choices that remain inside approved architecture/scope do not.

Environment repair that preserves the approved compatibility requirement does not automatically invalidate application approval.

## 6. Provider architecture

### 6.1 Provider role

Provider is a thin technology contract, not a second lifecycle engine and not an intelligent project-architecture agent.

A provider defines:

1. identity/version/contract version;
2. capabilities;
3. requirement schema;
4. deterministic compatibility resolution;
5. bootstrap dependencies;
6. environment requirements;
7. environment acceptance contract;
8. runtime actions;
9. normalized result/evidence envelope;
10. permission/consequence metadata.

Provider supplies technology facts. Planner chooses project architecture. Framework owns lifecycle/gates/evidence.

### 6.2 Provider origin and availability

v2.1.0 has no external provider marketplace/catalog or outsourced provider trust path.

Providers originate from:

- framework-created provider projects; or
- user-created/supplied provider projects.

A provider becomes locally available only after its managed project passes the applicable Blueprint/approval/implementation/verification/promotion lifecycle.

A locally promoted provider may be installed/activated automatically when an approved project requires its capability. Creating a previously nonexistent provider is architectural work requiring human approval.

### 6.3 Permission boundary

Provider declares required permissions; provider does not grant those permissions to itself. Framework policy and approved consequence/risk facts decide what execution receives.

## 7. Environment architecture

### 7.1 Environments are managed projects

Provider/test environments are normal framework-managed projects. Provider supplies requirements and acceptance contract; Planner/Tester/Coder/framework lifecycle creates, repairs, verifies, and promotes the environment implementation.

### 7.2 Family and generation

An **environment family** is a provider-defined normalized compatibility target.

An **environment generation** is one concrete immutable verified implementation of that family.

Compatible projects reuse the promoted generation. Incompatible requirements resolve to different families. A promoted generation is never modified in place; changes create a new generation.

### 7.3 Overlay isolation

Project-specific dependencies/build/runtime state normally live in isolated overlays on the reusable generation rather than creating a permanent family per project.

Dependencies may install automatically only when declared/bound by the approved Engineering Change Package.

Typical overlay content includes project dependencies, build/install output, test output, logs, temporary state, and caches.

### 7.4 Storage pressure and retention

The environment system is space-aware. It separates durable identity/evidence metadata from heavy artifacts.

Cleanup priority is conceptually:

1. stale disposable overlays;
2. expendable caches;
3. failed/unpromoted heavy artifacts after diagnosis needs end;
4. retired/deprecated unpinned generations;
5. previous rollback generations under stronger disk pressure.

The active promoted generation is protected. Previous known-good generations are retained when practical but need not consume disk forever. Artifact eviction must not delete generation identity, source/provenance, digests, promotion history, or required evidence.

Explicit pins may require retention/rebuildability guarantees beyond normal policy.

### 7.5 Failure ownership

Environment failure must not be recorded as candidate failure. If an unchanged candidate could not be validly evaluated because the environment failed, the evidence states that the candidate was **not evaluated**. The environment is repaired and the same candidate is retried where source remains unchanged.

## 8. Bootstrap capability graph and minimal core

### 8.1 Capability graph

Bootstrap/environment dependencies form an acyclic capability graph. A provider environment cannot require itself directly or indirectly. Previous generations may accelerate replacement but must not be the mandatory bootstrap dependency for rebuilding themselves.

### 8.2 `main-development`

`main-development` is the framework control plane. It contains only what framework operation itself requires, such as framework runtime, Git, basic filesystem/archive/hash/config/schema tooling, provider/capability resolution, project state/evidence handling, and generic execution interfaces.

It is not a universal developer workstation.

### 8.3 `generic-test`

`generic-test` is the minimal bootstrap/test substrate for generic checks and creation/verification of provider environments. It should not permanently contain domain SDKs/toolchains merely because projects may need them.

### 8.4 Two execution primitives

Core exposes two generic low-level abstractions:

- **ProcessExecutor** — bounded framework-owned local process execution for operations such as Git, schema validation, checksums, and framework maintenance commands.
- **EnvironmentBackend** — generic build/artifact/execution/input/output/evidence/resource/storage operations for isolated provider/project environments.

Docker may implement the first EnvironmentBackend but is not the provider contract.

### 8.5 Artifact versus execution

The backend separates immutable environment artifacts/generations from ephemeral execution instances. One promoted generation may support multiple isolated concurrent execution contexts.

### 8.6 Candidate immutability

Authoritative verification receives candidate content read-only or equivalent copy-on-write. Writable build/runtime/evidence state is isolated. Provider/environment code must not bypass the generic backend to obtain undeclared host/container privileges.

### 8.7 Authoritative verification

Required verification must run through the Blueprint-bound provider/environment capability. Incidental compatible tools present in `main-development` may support advisory Coder self-tests but cannot satisfy required `VER-*` obligations.

## 9. Agent roles and enforcement

### 9.1 Confirmed v2.1 intelligent roles

- Planner;
- Coder;
- Tester;
- Reviewer;
- Safety Reviewer when policy requires it.

Confirmed removals:

- `review_requester` — replaced by deterministic review/PR package assembly;
- `integration_tester` — Tester owns all `VER-*` verification regardless of execution type.

Provider is not an intelligent agent role.

Debugger is retained as an **on-demand diagnostic role** for ambiguous, conflicting, or repeated failures. It is not a mandatory pipeline stage; failures with clear ownership route directly to the responsible owner.

### 9.2 Role enforcement is not prompt-only

Each role is constrained by:

1. canonical role responsibility/policy;
2. role-specific input/context assembly;
3. tool/write/permission boundaries;
4. typed role-specific output artifacts;
5. workflow-transition validation.

A small common execution envelope may describe run execution facts, but semantic output types differ by role. The framework must not force Planner, Coder, Tester, Debugger, and Reviewer into one universal pass/fail/`not_applicable` decision schema.

### 9.3 Tester-to-Coder information split

Coder receives 100% of approved requirements, interfaces, observables, acceptance thresholds, constraints, and `VER-*` obligations.

Tester provides roughly 70% of concrete test information as development-facing handoff and retains roughly 30% of concrete cases/data/edge constructions outside normal Coder context for independent verification.

The split is not a mechanical file count. The human user may inspect all test artifacts. Retained tests cannot introduce undisclosed requirements.

### 9.4 Concrete test storage

Confirmed model:

- development-facing tests become maintained product regression tests in the product repository after approval and are protected from unilateral Coder modification;
- independent tests remain versioned framework-managed project knowledge outside normal Coder context;
- provider/environment acceptance tests remain provider/environment-project artifacts.


## 10. Failure routing and replanning

Failures route to the owner of the invalid artifact or capability rather than automatically through one generic diagnosis path.

- candidate implementation defect -> Coder;
- architecture/requirement defect -> Planner/user and new approval when approval-bound design changes;
- test implementation defect -> Tester;
- environment defect -> environment project lifecycle;
- bootstrap capability defect -> lower-level capability owner;
- provider contract defect -> provider project maintenance;
- ambiguous/conflicting ownership -> on-demand Debugger.

Repeated materially equivalent failures must not loop indefinitely. Exact retry/escalation thresholds remain open.

## 11. Artifact dependency graph and targeted invalidation

### 11.1 Typed dependency DAG

Framework maintains a typed directed acyclic dependency graph across requirements, Blueprint elements, plans, test designs, implementation traces, candidate SHAs, environments, evidence, reviews, approvals, and baselines.

Expected semantic relationships include concepts such as:

- `derived_from`;
- `implements`;
- `verifies`;
- `constrains`;
- `executes_on`;
- `materialized_from`;
- `generated_from`;
- `approved_as_part_of`.

Exact schema names are implementation details.

### 11.2 Validity states

At minimum:

- `CURRENT`;
- `STALE`;
- `SUPERSEDED`;
- `INVALID`.

An upstream change normally makes declared descendants `STALE`, not automatically invalid. The owning role reevaluates stale artifacts.

### 11.3 Targeted invalidation

Only declared semantic descendants become stale. Unrelated current artifacts remain reusable. Planner receives an affected subgraph plus preserve set for targeted replanning, while still reconciling all applicable requirements.

Candidate changes invalidate candidate-bound evidence, not unchanged architecture. Environment-generation changes invalidate environment-bound evidence, not application approval when compatibility requirements are unchanged.

### 11.4 Explanatory CLI output

The framework should explain why an artifact is stale/blocked, including dependency path and required owner, rather than emitting only raw JSON state.

## 12. Project Baselines / Savepoints

Long-lived projects must not keep all historical revisions in the active working graph forever.

A **Project Baseline / Savepoint** captures the current effective engineering frontier at a stable point, including current requirement/Blueprint heads, candidate/release identity where applicable, environment/provider bindings, approval state, verification/review summaries, and graph/archive root identity.

Completed history represented by the baseline may be compacted into immutable compressed archive packs. History remains addressable; compaction is not deletion.

The latest baseline becomes the normal active dependency frontier for subsequent work.

Baselines should be user-creatable and may be framework-suggested after releases, major milestones, or graph-size thresholds. The framework should not silently compact unresolved active work.

## 13. Graph visualization and future VS Code UI

v2.1.0 requires a real **static graph projection** from canonical graph data. Focused views are more useful than attempting to render the entire graph at once.

Expected views include:

- overview;
- requirements/architecture;
- verification;
- current work item;
- failure path;
- environment;
- approval;
- full active graph;
- baseline/history comparison.

A future interactive VS Code graph is an explicit roadmap target. It must use the same canonical graph/query/action API as CLI/static rendering and must never become a separate source of truth.

Future GUI actions such as inspect, filter, approve/reject, request change, propose an edge change, edit semantic content, or create a baseline require a separate interaction-policy design. Protected identity/integrity fields cannot become arbitrary drag-and-drop edits.

## 14. Graph scale, compression, and integrity

v2.1 implementation verification must exercise graph sizes around:

- 1,000 nodes;
- 10,000 nodes;
- 100,000 nodes;
- a large archived-history scenario around 1,000,000 historical nodes/revisions where practical.

Measure load/save, traversal, affected-subgraph calculation, stale propagation, cycle detection, baseline creation, compaction/archive, restore/query, rendering, memory use, and storage size.

Archived structured graph metadata may be compressed. Heavy evidence/artifacts should use content-addressed references/deduplication where practical.

v2.1 prioritizes **tamper-evident integrity** before broad encryption: schemas, controlled writes, immutable history, content/root digests, and explicit validity handling. Future security work may add signatures/MACs/authenticated metadata and encryption at rest. Encryption is not a substitute for integrity and authorization.

## 15. Final Acceptance Suite

The confirmed final promotion guard is documented in `final-acceptance-suite.md`.

The required model is:

- targeted authoritative verification remains the primary requirement-level verification mechanism;
- before promotion, every candidate also runs a small project-defined Final Acceptance Suite selected from existing `VER-*` obligations;
- the suite covers basic viability, critical end-to-end behavior, high-consequence obligations, and deployment/runtime sanity;
- it is bound to the exact candidate SHA and required environment generation(s);
- environment failure means acceptance not evaluated, not candidate failure;
- full-suite verification remains a separate policy-triggered operation;
- final acceptance may expose missing dependency edges and therefore improve the graph model.


## 16. Framework self-development

The framework's initial self-Blueprint reserves stable `REQ-FW-*`, `CMP-FW-*`, `IFACE-FW-*`, and `VER-FW-*` identities. The eventual machine-readable canonical Blueprint must preserve those identities with lineage rather than replacing them silently.

A stable accepted framework controls candidate framework development/verification/promotion. Candidate framework code cannot weaken its own approval gates or self-declare promotion.

Architecture documentation must describe implemented behavior truthfully. Future-design documents remain separate until implementation is accepted.

## 17. Migration and v2.1 acceptance direction

v2.1 release acceptance must verify, at minimum:

- no new technology name is required in generic core to support a synthetic unknown provider;
- neutral project creation works;
- ProjectBlueprint/Plan separation and traceability work;
- provider/environment family/generation lifecycle works;
- environment failures do not create false candidate defects;
- authoritative verification cannot fall back to incidental control-plane tools;
- role-specific output/workflow enforcement works;
- removed roles do not remain required workflow stages;
- confirmed Tester test-code ownership/storage boundaries are enforced;
- clear failures bypass Debugger while ambiguous/conflicting/repeated failures can invoke the on-demand diagnostic role;
- every promotable candidate is blocked until its exact candidate/environment-bound Final Acceptance Suite passes;
- targeted stale propagation preserves unaffected artifacts;
- baseline/archive restores historical traceability;
- static graph views come from canonical graph data;
- graph scale/performance is measured rather than assumed;
- framework self-development follows the same lifecycle it enforces.

Exact final acceptance thresholds, CLI spellings, serialization formats, and other implementation-level mechanics are resolved only through the open-decision process.

## 18. Confirmed versus open snapshot

### Confirmed architecture areas

- project compatibility boundary;
- technology-neutral modular core;
- neutral project creation;
- ProjectBlueprint/Plan separation;
- universal stable-ID traceability;
- Engineering Change Package approval model;
- user-authoritative environment choices;
- locally created/promoted providers only, no external provider marketplace;
- providers as thin contracts and provider projects;
- environments as managed projects with families/immutable generations;
- approved isolated project overlays and automatic declared dependency installation;
- space-aware environment retention;
- minimal `main-development` / `generic-test` and generic EnvironmentBackend;
- authoritative provider-bound verification;
- Planner/Coder/Tester/Reviewer/Safety Reviewer roles;
- removal of Review Requester and Integration Tester;
- 70/30 concrete Tester-to-Coder information split with 100% requirement transparency;
- confirmed test-code ownership: development-facing tests in the product repository, independent verification tests in framework-managed project knowledge, and provider acceptance tests separate;
- on-demand Debugger for ambiguous/conflicting/repeated failures only;
- mandatory project-defined Final Acceptance Suite on every promotable candidate;
- typed artifact dependency DAG and targeted invalidation;
- Project Baselines/savepoints, archive/compaction, compression/dedup direction;
- static v2.1 graph visualization and future VS Code projection;
- graph scale/performance acceptance concern;
- tamper-evident integrity before broad encryption;
- framework self-development through its own lifecycle.

### Open architecture areas highlighted by this consolidation

- canonical ProjectBlueprint/provider/role schemas and storage locations;
- lifecycle state-machine source of truth;
- generic risk/permission metadata;
- repair/replan retry limits;
- final CLI surface;
- exact release packaging/base commit;
- precise scope of deferred security/HIL/remote-CI/self-upgrade/VS Code interaction work.

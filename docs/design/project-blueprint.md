# ProjectBlueprint Specification

Status: **pre-implementation normative design**
Last updated: **2026-09-29**

## Purpose

`ProjectBlueprint` is the Planner-owned, revisioned description of the approved technical shape of a project.

The Blueprint answers:

> What must the resulting project be, expose, constrain, and prove?

The implementation Plan answers:

> How will the current project state be changed to reach the approved Blueprint?

Blueprint and Plan are separate authoritative artifacts. A project may receive many implementation Plans while continuing to use the same approved Blueprint revision.

## Ownership

The **Planner creates and revises ProjectBlueprint**.

Other actors contribute facts and findings but do not silently edit architectural intent:

- **User** defines product requirements and material deployment/environment constraints and may edit or request changes to any semantic part of the approval package.
- **Provider** supplies technology capability facts, compatibility constraints, environment requirements, and acceptance contracts.
- **Tester** supplies testability findings and concrete test design.
- **Coder** supplies implementation-feasibility findings and implements only the approved architecture.
- **Framework** validates identity, traceability, dependency integrity, revision history, approval status, and candidate/evidence bindings.

If Provider, Tester, or Coder finds the Blueprint infeasible or inconsistent, it emits a structured finding. Planner is the actor that reconciles the finding with original requirements and produces a revised Blueprint.

## Blueprint versus Plan

A Blueprint describes stable or intentionally changed project architecture, for example:

- environment/deployment requirements;
- repository/module structure;
- components and responsibilities;
- interfaces and externally meaningful contracts;
- provider/capability requirements;
- risk-relevant architectural facts;
- verification obligations;
- requirement-to-design traceability.

A Plan describes a specific change procedure, for example:

- scaffold a module;
- modify a component;
- migrate data;
- implement an interface;
- execute an approved verification sequence.

An implementation-only correction may reuse the current Blueprint. A change to architecture, public interfaces, deployment constraints, provider capability requirements, risk/permission characteristics, or verification obligations requires a Blueprint revision.

## Stable architecture element IDs

Every project, including small projects, uses stable traceability identifiers.

Minimum identifier classes are conceptually:

```text
REQ-*       requirement
CMP-*       component/module responsibility
IFACE-*     interface/contract
VER-*       verification obligation
```

Additional classes such as `TASK-*`, `TEST-*`, or `IMP-*` may be introduced by the concrete schema, but requirements, components/interfaces, and verification obligations must remain traceable in every project.

IDs are **framework-managed identity metadata**, not casual user-editable labels.

Rules:

1. The same conceptual element keeps the same ID across revisions even when its description evolves.
2. Splitting one conceptual element into multiple elements allocates new IDs for the new identities and records lineage.
3. Merging elements records lineage from old IDs to the new/current identity.
4. Deleted/retired IDs are never silently reused for a different meaning.
5. User-visible names/titles may change without changing the stable ID.
6. Direct edits to IDs, hashes, revision numbers, provenance records, or dependency-integrity metadata are rejected or regenerated by the framework rather than trusted as authoritative user content.

## Requirement traceability is a core framework specification

Every project must be able to answer, for each applicable requirement:

```text
Requirement
  -> Blueprint component/interface
  -> Plan task / implementation mapping
  -> Candidate implementation
  -> Verification obligation
  -> Test/evidence result
```

The framework must generate and validate a traceability matrix from these linked records.

A requirement may not disappear merely because implementation completed. Every requirement in the approved change scope must end in one of the explicit states defined by the future schema, such as satisfied/verified, deferred by approved decision, or not-applicable with an approved rationale.

This traceability model is intended to support auditable engineering processes and future certification-oriented workflows. It does **not** by itself claim compliance with, or certification to, any ISO or other external standard; certification requirements must be mapped explicitly when a project targets a particular standard.

## How implementation traceability is enforced

Coder must return a structured implementation trace for the approved change.

At minimum it must map:

- implemented Blueprint element IDs to concrete repository artifacts (paths and, where practical, symbols/components);
- applicable requirement IDs to the implementation elements that satisfy them;
- changed production artifacts to the Blueprint/Plan elements that authorize the change;
- implementation obligations that were not completed, with an explicit reason rather than omission.

The framework independently validates what it can:

1. changed paths come from the candidate Git diff rather than Coder assertion alone;
2. all implementation trace IDs exist in the approved Blueprint/Plan;
3. every required in-scope Blueprint element has an implementation mapping or an explicit approved disposition;
4. changed production artifacts are within approved scope and are associated with an approved change element;
5. the implementation trace is bound to the candidate SHA.

Tester then maps concrete tests/evidence to `VER-*` and applicable `REQ-*`/`CMP-*`/`IFACE-*` IDs. Verification cannot be considered complete while mandatory trace links are missing.

Reviewer and Debugger consume the same IDs so a defect can be traced back through requirement, design, implementation, and evidence without relying on prose matching.

## Interfaces are first-class Blueprint objects

Interfaces include any externally meaningful contract between components or with users/systems, including:

- APIs and function/service contracts;
- messaging topics/services/actions;
- CLI contracts;
- protocols and network boundaries;
- file/data formats;
- database/data schemas;
- configuration schemas;
- plugin/provider interfaces;
- hardware-facing contracts.

An interface has a stable `IFACE-*` identity, providers/consumers where relevant, constraints, and traceability to requirements and verification obligations.

## Verification requirements belong in the Blueprint

Blueprint defines **what must be proven**, not the detailed test implementation.

Examples:

```text
VER-BUILD: project builds successfully for the approved target
VER-CADENCE: publisher produces 10 Hz +/- approved tolerance
VER-SHUTDOWN: application terminates cleanly within approved limit
```

Tester owns **how to prove it** by creating test specifications, concrete test cases, fixtures, independent verification cases, and evidence expectations.

Provider may contribute domain-specific acceptance capabilities and constraints, but Provider does not redefine the project's verification obligation.

This separation prevents Planner from doing Tester's work while ensuring Tester receives an unambiguous, traceable verification target.

## Environment and provider requirements

Blueprint stores the approved environment/capability **requirements**, not normally a mutable infrastructure generation.

Example concept:

```yaml
environment_requirement:
  capability: ros2
  constraints:
    distribution: humble
  selection:
    authority: user
```

Provider resolves the approved requirement to a compatible environment family/generation at execution time.

Changing the approved target (for example one incompatible distribution/platform to another) is an architectural Blueprint change. Replacing a broken environment generation with another generation that satisfies the same approved compatibility requirement is infrastructure lifecycle work and does not, by itself, revise the project Blueprint.

## Risk-relevant architecture facts

Blueprint records consequence-relevant facts such as:

- physical hardware access required;
- physical motion possible;
- flashing/destructive device operation possible;
- privileged host access required;
- externally destructive data operation possible;
- network/external production access required.

Blueprint does not encode technology-name shortcuts such as `firmware => R3`.

Framework policy combines Blueprint facts, provider permission metadata, and requested operations to derive risk/gates. Hardware/risk design may be refined by later hardware projects without weakening this consequence-based rule.

## Planner artifact boundary

Planner may create **proposed engineering/design artifacts** when they are needed to make architecture precise and reviewable.

Allowed Planner outputs include:

- ProjectBlueprint structured data;
- architecture Markdown and Mermaid diagrams;
- interface/API/data schemas;
- OpenAPI/IDL/Protocol Buffer/ROS message-style declarative contracts;
- configuration schemas and configuration contracts;
- repository/module layout specifications;
- deployment/environment requirement specifications;
- verification obligations and acceptance criteria;
- proposed scaffold descriptions;
- other declarative engineering artifacts that define architecture or contract.

Planner must **not** perform downstream implementation work:

- no production algorithm/business-logic implementation;
- no executable test implementation owned by Tester;
- no provider/environment implementation owned by Coder/provider project workflow;
- no unapproved mutation of the product repository;
- no hidden build/install procedure that bypasses Provider/Coder feasibility.

When an exact declarative contract is itself part of architecture (for example an API schema, `.proto`, message definition, or configuration schema), Planner may produce the complete proposed artifact in the approval package. It is staged as design input. Materialization into the product repository occurs only after approval through the authorized scaffold/Coder path and remains subject to feasibility and traceability checks.

A build/configuration file may be drafted by Planner only to the extent that it is an architectural/configuration contract. Executable build logic and technology-specific implementation remain Provider/Coder responsibility.

## Repository structure ownership

Planner defines structurally meaningful repository/module boundaries and contract artifacts. Planner does not need to predict every internal source file.

Conceptually:

```text
Planner owns:
  module root
  public/structural manifests
  interface locations/contracts
  test/verification structure requirements

Coder owns within approved scope:
  internal source decomposition
  helper files
  implementation symbols
  internal algorithms
```

This keeps the Blueprint useful for coordination/debugging/update without making it a substitute for implementation.

## Revision model

Blueprint is revisioned:

```text
blueprint-r001
blueprint-r002
...
```

Each revision records:

- parent revision;
- authoritative request/document inputs;
- repository baseline or applicable project-knowledge revision;
- changed architectural element IDs;
- added/retired IDs and lineage;
- planner decisions and assumptions;
- validation/feasibility results used to make the revision approval-ready.

Planner replanning must explicitly confirm that the revised Blueprint and Plan still satisfy the original applicable requirements, plus any later approved requirement revisions. The framework must mechanically check traceability coverage and report any requirement that loses a design or verification link.

## When a Blueprint revision is required

Typical Blueprint-changing work includes:

- new project architecture;
- new/removed major component;
- public/interface contract change;
- deployment/runtime target change;
- provider/capability requirement change;
- risk/permission characteristic change;
- verification obligation change;
- architectural repository/module boundary change.

Typical Plan-only work may include an internal defect fix or implementation change whose approved architecture, interfaces, environment, risk, scope boundaries, and verification obligations remain unchanged.

Planner makes the semantic determination, and the framework records it. A claim of `blueprint_change: false` must be reviewable against the current Blueprint and diff.

## Persistent project knowledge

An approved and implemented Blueprint becomes authoritative project knowledge for later work. It must not remain only in historical work-item output.

Future Planner runs receive the current approved ProjectBlueprint and its traceability graph as input.

The concrete persistent paths are still an implementation/schema decision, but the information must survive individual work items and remain versioned with the project/framework knowledge model.

## Editable semantic content versus managed integrity metadata

User must be able to modify or request modification of any **semantic part** of the approval package, including:

- requirements;
- environment constraints;
- component responsibilities;
- interfaces;
- architecture decisions;
- verification obligations;
- implementation scope;
- Plan content;
- assumptions and rationale.

User may edit directly through supported tooling or ask an agent to revise the package.

Framework-managed integrity/identity fields are not direct semantic editing surfaces:

- stable IDs;
- hashes;
- revision sequence/provenance;
- candidate SHA bindings;
- signature/integrity records;
- machine-derived dependency edges when they can be deterministically regenerated.

A user can request semantic restructuring that causes IDs/lineage/dependencies to change, but the framework performs and records those identity changes rather than trusting arbitrary hand-edited identifiers.

## Representations

ProjectBlueprint needs one canonical machine-readable representation plus human-readable views.

The machine-readable form is authoritative for identity, traceability, dependency validation, diffing, and automation.

Markdown/Mermaid and other design artifacts are human-reviewable project knowledge linked to the same Blueprint elements. A future editing workflow may allow human edits to these views to propose Blueprint revisions, but it must reconcile them back into the canonical structured model before approval.

## Pre-approval validation

Before a package can become approval-ready, framework runs at least:

1. Blueprint/schema and identity validation;
2. traceability completeness checks;
3. provider/capability feasibility;
4. Tester testability/test-design feasibility;
5. Coder implementation feasibility;
6. Planner reconciliation of findings with original requirements;
7. risk/permission classification and required gates;
8. final dependency/verification coverage validation.

Planner may need several draft revisions during this loop. These drafts do not require human approval individually.

Only a final approval-ready package is presented for human approval.
